# SoundFit 스펙 v1.1 — v1.0 대비 변경 사항

작성일: 2026-08-01 · 대상 문서: *Personalized AI Music Platform — Product Requirements & Technical Specification v1.0*
성격: v1.0을 대체하지 않는 **델타 문서**. 바뀐 결정과 그 근거만 담습니다.

---

## 0. 이 문서를 읽는 방법

v1.0은 제품 방향과 위험 인식이 이미 상당히 정확한 문서입니다. 특히 이 세 가지 판단은
그대로 유지합니다.

- 초기 시장을 **선물 노래**로 좁힌 것 (지불 이유가 명확한 유일한 진입점)
- **보이스 클로닝을 MVP에서 제외**한 것
- **프로바이더 어댑터 + capability registry**를 처음부터 요구한 것

v1.1이 하는 일은 방향을 바꾸는 게 아니라, **문장으로만 존재해서 구현 단계에서 반드시
해석 충돌이 나는 부분들을 결정으로 바꾸는 것**입니다. 아래 16개 항목이 전부입니다.

각 항목의 형식:

> **문제** → v1.0에서 무엇이 비어 있거나 서로 모순되는지
> **결정** → v1.1에서 어떻게 정했는지
> **검증** → 이 리포지토리의 프로토타입에서 실제로 강제되는지 (`soundfit/`)

## 1. MVP의 보컬이 무엇인지 정의되어 있지 않다 (내부 모순)

**문제**
§7.2는 보이스 클로닝을 MVP 범위에서 제외합니다. 그런데 §8.3은 "보컬 타입 선택"을,
§8.6은 "보컬을 더 따뜻하게"를 제공하고, §6.1은 보컬 캐릭터를 Music DNA 차원으로
정의합니다. **그러면 MVP에서 노래하는 주체가 누구인지가 문서 어디에도 없습니다.**
이건 사소한 누락이 아니라 원가, 법무, 품질, 프로바이더 선택을 전부 좌우하는 결정입니다.

**결정**
보컬 조달을 4단 등급으로 정의하고, 각 등급의 선행 조건을 명시합니다.

| 등급 | 실제 인물 복제 | MVP | 활성화 선행 조건 |
|---|---|---|---|
| `synthetic_guide` 합성 가이드 보컬 | 아니오 | **제공** | 없음. AI 생성 고지 필수 |
| `licensed_stock_voice` 라이선스 스톡 보이스 | 아니오 | 미제공 | 가수·성우와의 서면 계약(모델 학습·상업 사용 범위 포함) |
| `self_voice_clone` 본인 목소리 클론 | 예 | 미제공 | 본인 동의 + 신원·라이브니스 검증 + 철회 경로 |
| `third_party_clone` 제3자 목소리 클론 | 예 | 미제공 | 위 + 대상자 직접 동의. `memorial`·공인은 **영구 금지** |

MVP는 `synthetic_guide` 하나만 활성화합니다. 이 결정의 실제 의미는
**"MVP는 보컬 품질로 경쟁하지 않는다"**이며, 그렇다면 상품 구성과 가격 문안에서
"완성된 노래"가 아니라 "가사 + 편곡 + 가이드 보컬"로 표현해야 합니다.
(라이선스 스톡 보이스를 Phase 2에 넣고 싶다면 Phase 0에 **가수 계약 협상**을 추가해야
하며, 이것이 11–13주 일정이 낙관적인 첫 번째 이유입니다. → §16)

**검증** `domain/rights.js`의 `VOICE_MODES` / `checkVoiceRequest()`.
클론 계열 3개 등급은 모두 `allowed:false` + 선행 조건 목록을 반환하고, 테스트가 이를 강제합니다.

## 2. "controlled musical differences"가 정의되어 있지 않다

**문제**
§7.1과 §8.5는 "통제된 음악적 차이를 가진 두 버전"과 "차이를 쉬운 말로 설명"을 요구합니다.
그런데 무엇을 통제하는지가 없습니다. 정의가 없으면 구현은 거의 확실히
"씨드 두 개로 두 번 생성"이 되고, 그 순간 **차이를 설명할 수 없고, A/B 선택 데이터를
취향 학습에 쓸 수도 없습니다**(무엇 때문에 골랐는지 모르니까).

**결정** A/B 변형 정책을 다음과 같이 고정합니다.

1. A와 B는 **같은 씨드, 같은 가사, 같은 곡 구조**를 공유한다.
2. 차이는 **선언된 변형 축(variation axis)에서만** 발생하고, **정확히 2개 축**만 다르다.
3. 각 축은 한국어·영어 설명 문장을 함께 가진다. UI 문구를 따로 쓰지 않는다.
4. 어떤 축이 선택되었는지를 `GenerationRun`에 기록해, A/B 선택률을 **축 단위로** 집계한다.
5. 곡 구조(템플릿)는 **변형 전 기준 템포**로 결정한다.

5번은 실제로 프로토타입에서 발견한 버그입니다. 템포 축(+7 BPM)이 걸리자 길이 맞춤
로직이 다른 구조 템플릿을 골라서, B가 10구간이 아니라 11구간(솔로 포함)이 되었습니다.
"2개 축만 다르다"는 약속이 조용히 깨진 것이고, 이건 사양서로는 절대 안 잡히고
구현해 봐야 나오는 종류의 문제입니다.

현재 축 레지스트리: `arrangementDensity`, `chorusLift`, `leadInstrument`, `rhythmFeel`, `tempoDelta`.

**검증** `domain/spec.js`의 `AB_AXES` / `makeVariantPair()`.
테스트 "A and B differ on exactly the declared axes and nothing else"가
variation 외 모든 필드의 동일성을 비교합니다.

## 3. 구간 단위 수정의 실행 모델이 없다

**문제**
§5는 "수정은 국소적이어야 한다"를 원칙으로 세우고, §23은 프로바이더가 구간 수정을
지원하지 않을 때 "capability detection과 명확히 범위가 정해진 전체 재생성 폴백"을
완화책으로 제시합니다. 그런데 **무엇이 국소적으로 바뀌었는지 판단하는 방법이 없습니다.**
의도(intent)가 "후렴만"이라고 선언한다고 실제로 후렴만 바뀌는 게 아닙니다.

**결정** 선언이 아니라 **콘텐츠 해시 비교**로 판단합니다.

```
MusicSpec ──arrange()──▶ Score(구간 배열, 구간별 cacheKey)
                              │
                    cacheKey = hash(구간의 모든 노트 + 트랙 레벨 + 톤 + BPM + 조성)
                              │
            diffScores(이전 Score, 새 Score) ──▶ { changed[], unchanged[], structural }
                              │
      resolveExecutionPlan(프로바이더 capability, changed 수)
                              │
             section_patch(변경 구간만) 또는 full_regenerate(전체)
```

핵심 규칙 세 개:

- **cacheKey에는 들리는 모든 것이 들어가야 한다.** 노트 개수만 넣으면 음높이 변경이
  캐시를 무효화하지 못해 조용히 옛 오디오가 남습니다. (구현 중 실제로 이 실수를 했습니다.)
- **의도의 선언된 scope를 신뢰하지 않는다.** 예: "후렴을 더 감정적으로"에서
  스트링을 전역으로 올리면 모든 구간이 dirty가 됩니다. 그래서 악기 레벨 변경도
  `sectionOverrides[구간].levels`로 **구간에 스코프**됩니다.
- **폴백은 사용자에게 고지한다.** 전체 재생성이 필요하면 소요 시간과 이유를 먼저 보여줍니다.

**검증** 브라우저 실측: "후렴을 더 힘있게" → **10구간 중 3구간(chorus1·2·3)만 재렌더**,
21초. 가사 한 줄 수정 → **verse2 1구간만** dirty. 기타 솔로 추가 → `structural: true`로
정직하게 전체 재생성. 테스트 5개가 이를 강제합니다.

## 4. 상태 기계에 실패·환불·만료 경로가 없다

**문제**
§10.1의 상태 기계는 행복 경로만 있습니다. `Generating`에서 프로바이더가 타임아웃되면?
`Blocked`에서 사용자가 환불을 요청하면? 결제 후 3주간 방치된 초안은?
운영에서 실제로 발생하는 상태가 전부 빠져 있습니다.

**결정** 상태와 허용 전이를 전부 열거하고, **불법 전이는 예외로 차단**합니다.

```
intake → story_approved → lyrics_draft → lyrics_approved → generating
                                                              ├→ safety_check → comparison → revising ⇄ safety_check
                                                              │                     ├→ finalized → licensed → delivered
                                                              │                     └→ (comparison 복귀)
                                                              └→ generation_failed → generating | refunded
safety_check → blocked → lyrics_draft | refunded
safety_check → quarantined → generating | refunded
licensed | delivered → refunded
intake | lyrics_draft → expired            (초안 TTL)
모든 상태 → deleted                          (사용자 삭제 요청)
```

추가된 상태: `generation_failed`, `blocked`, `quarantined`, `refunded`, `expired`, `deleted`.

**검증** `core/store.js`의 `STATES` / `canTransition()` / `setProjectState()`.
브라우저 실측 이력: `intake → story_approved → lyrics_draft → lyrics_approved →
generating → safety_check → comparison → revising → comparison → finalized → licensed`.

## 5. 결제·엔타이틀먼트 모델이 데이터 모델에 없다

**문제**
§18에 "유료 생성 요청에 멱등성 키를 사용한다", "프로바이더 잡 타임아웃 시 중복 과금 방지"가
한 줄씩 있습니다. 하지만 §12 데이터 모델에는 `Order`, `Entitlement`, `IdempotencyKey`가
없습니다. **엔티티가 없으면 그 요구사항은 구현되지 않습니다.**

**결정** 다음 엔티티를 추가하고, 유료 연산은 전부 멱등성 래퍼를 통과시킵니다.

| 엔티티 | 핵심 필드 |
|---|---|
| `Order` | id, projectId, tier, amount, currency, provider, providerRef, status, paidAt, refundedAt |
| `Entitlement` | projectId, orderId, includedVariants, includedRevisions, usedRevisions, regenerationCredits, expiresAt |
| `IdempotencyKey` | key, operation, status(in_flight/completed/failed), startedAt, completedAt, result, attempt |
| `CostLedgerEntry` | projectId, stage, provider, model, units, costUsd, ms, meta |
| `ShareLink` | id, projectId, tokenHash, expiresAt, revokedAt, openCount |
| `ProviderCapability` | providerId, version, capabilities, commercial, cost, latency, readiness |

멱등성 키 규칙: `키 = (projectId, operation, 입력 해시)`.

- `completed` → 저장된 결과를 재생하고 **과금·생성하지 않는다**
- `in_flight` + 2분 이내 → 진행 중임을 알리고 새 잡을 만들지 않는다
- `in_flight` + 2분 초과 → 죽은 시도로 판단해 회수(reclaim)하고 감사 로그를 남긴다
- `failed` → 재시도 허용, 과금은 하지 않는다

`GenerationRun`에도 `externalJobId`, `idempotencyKey`, `attempt`를 추가합니다.
비동기 콜백 정합(§18)은 이 필드 없이는 불가능합니다.

**검증** `core/store.js`의 `withIdempotency()`. 엔지니어링 패널의 "멱등성" 탭에서
키 상태를 직접 볼 수 있고, 결제 후 같은 요청을 다시 하면 재생 경로를 탑니다.

## 6. `privacyMode`와 `prohibitedDetails`가 강제되지 않는다

**문제**
§12는 `SongProject.privacyMode`와 `StoryBrief.prohibitedDetails`를 정의하지만,
`privacyMode`의 값이 무엇인지, `prohibitedDetails`가 **누가 언제 어떻게** 검사하는지가
없습니다. §17은 "민감 텍스트를 운영 로그에서 마스킹"을 요구하지만 무엇이 민감인지
분류 체계가 없습니다.

**결정** 인테이크의 **필드마다** 데이터 분류를 부여하고, 분류가 보관·로그·암호화를 결정합니다.

| 분류 | 보관 | 로그 | 가사 사용 |
|---|---|---|---|
| `personal_basic` | 365일, 암호화 | 마스킹 | 가능 |
| `personal_sensitive` | 180일, 암호화 | **기록 안 함** | 명시적 포함 동의 필요 |
| `never_store` | **저장 안 함**(세션 내 생성에만) | 기록 안 함 | 금지 항목으로만 사용 |

- "절대 넣지 말 것" 답변은 `never_store`입니다. 금지 목록을 영구 보관하는 것 자체가
  가장 민감한 정보를 영구 보관하는 일이라서, 별도 `ephemeral` 객체로 분리해
  영속화 코드가 한 곳에서 버립니다.
- `privacyMode`: `private`(기본) / `strict`(민감 분류 값을 저장하지 않음) / `shared`(공유 링크 발급됨).
- **금지 항목이 가사에 등장하면 승인 버튼이 비활성화됩니다.** 경고가 아니라 차단입니다.
- 자동 스캔: 전화번호, 이메일, 주민등록번호 형식, 카드번호 형식, 상세 주소, 전체 날짜,
  건강 관련 표현, 회사명.

**검증** `domain/story.js`의 `CLASSIFICATIONS` / `scanSensitive()` / `persistable()`,
`domain/lyrics.js`의 `reviewLyrics()`. 테스트: 금지어를 가사에 넣으면 `canApprove:false`.

## 7. 유사도 게이트의 배치가 문서 안에서 모순된다

**문제**
§10.1 상태 기계는 `SafetyCheck`를 생성 직후 필수 단계로 둡니다. 그런데 §21 로드맵은
Similarity Gate를 **Phase 3**에 배치합니다. Phase 2 유료 MVP는 안전 검사 없이
출시된다는 뜻이 되고, 이건 §23의 최상위 위험 항목과 직접 충돌합니다.

**결정** 게이트를 두 단계로 쪼갭니다.

- **Phase 1부터**: 상징적(멜로디 인터벌 n-gram) 사전 검사. 비용이 거의 0이고
  격리 경로·재생성 경로·증거 기록 구조를 미리 완성할 수 있습니다.
- **Phase 3**: 라이선스된 카탈로그 대상 오디오 지문. 여기서 비용과 계약이 발생합니다.
- **불변 규칙**: 어떤 형태의 게이트도 없이 유료 다운로드를 제공하지 않는다.
  판정은 `pass` / `review` / `quarantine` 3값이고, 결과와 검출기 버전은 전달물에 포함됩니다.

**정직하게 남겨둘 한계**: 상징적 검사는 편곡·음색 표절을 잡지 못합니다.
프로토타입의 참조 세트는 공개 도메인 전래 멜로디(테스트 픽스처)입니다.

**검증** `audio/fingerprint.js`. 테스트: 생성 멜로디는 `pass`,
참조 모티프를 그대로 복사한 멜로디는 `quarantine`.

## 8. 프로바이더를 유료 트래픽에 붙일 조건이 없다

**문제**
§11.2와 §21 Phase 0은 상업적 사용 조건, 데이터 보관, 지역 제한을 "평가한다"고만 합니다.
평가 결과가 **어디에 저장되고 누가 그것을 검사하는지**가 없으면, 실무에서는
"일단 붙여보고 나중에 확인"이 됩니다.

**결정** capability registry에 `commercial` 블록을 필수로 두고, **준비 게이트**를 통과하지
못한 프로바이더는 유료 트래픽 라우팅을 코드 수준에서 거부합니다.

차단 조건 6개: `commercialUseAllowed !== true`, 계약서 미보유,
사용자 데이터 학습 사용 여부 미확정, 보관 기간 불명, 서비스 지역 불명, 단가 불명.

이 값들은 마케팅 페이지가 아니라 **서명된 계약서**에서만 채웁니다.
`termsVersion`을 함께 저장해, 약관이 바뀌면 게이트를 다시 통과해야 합니다.

**검증** `domain/capability.js`의 `readinessGate()`.
예시 엔트리 `provider-a`는 `commercial_use_unverified`, `no_contract_on_file` 등으로
차단되고, 테스트가 이를 확인합니다.

## 11. 접근성과 다국어 요구사항이 전혀 없다

- 색상만으로 상태를 전달하지 않는다(유사도 판정 배지에 텍스트 병기).

**검증** `domain/lyrics.js`의 `countSyllables()`(ko/en/ja),
`assets/css/app.css`의 reduced-motion 블록, 스튜디오의 `aria-live`·`aria-pressed`.

## 12. 가사 품질을 어떻게 판정하는지 없다

|---|---|---|

회귀 비교하고, **금지어 위반율은 0이 아니면 배포 불가**입니다.

## 13. 추모(memorial) 상황과 보컬 정책이 충돌한다

**문제**
§8.1은 "추모·기억"을 프리셋 상황으로 제공합니다. §15는 고인 음성 재현에 "더 엄격한 통제
또는 금지"를 적용한다고 합니다. **가장 감정적으로 강력한 상황이 동시에 가장 위험한 요청을
유발하는 상황인데**, 둘 사이 규칙이 "또는"으로 남아 있습니다.

**결정**

- `memorial` 상황에서는 **어떤 등급의 인물 음성 재현도 영구 금지**합니다("더 엄격"이 아니라 금지).
- 상황을 선택하는 화면에서 미리 고지합니다. 결제 후에 거절하면 최악입니다.
- 스크리닝 패턴에 "돌아가신/고인/하늘에 계신 + 목소리"를 **차단(block)** 으로 넣습니다.
- 대체 경로를 제시합니다: 가사와 편곡으로 그 사람을 기억하는 방식.

**검증** `domain/rights.js`의 `deceased_voice` 패턴(block),
`VOICE_MODES.third_party_clone.prohibitedFor: ['memorial', 'public_figure']`,
상황 선택 화면의 사전 고지.

## 14. 인물 이름 요청을 어떻게 처리할지의 방법론

**문제**
§16.1은 "아티스트 이름 프롬프트를 허용된 음악적 속성으로 변환한다"고 합니다.
방법이 없으면 구현은 **유명인 이름 목록**이 되고, 그 목록은 유지 불가능하며
로케일을 벗어나면 무력하고, 목록 자체가 정책 유출입니다.

**결정** 이름이 아니라 **요청의 형태(의도 패턴)** 를 탐지합니다.

- `<무엇이든> + 처럼/같은/스타일로/목소리로 + 불러/노래` → `transform`
  (거절이 아니라 속성 변환: 템포 범위, 악기 구성, 시대적 사운드, 정서, 보컬 결)
- `목소리 + 복제/클론`, `그대로/똑같이/카피`, 고인 음성 → `block`
- 어떤 경우에도 **"누구처럼 들리게 해준다"고 약속하지 않습니다.**

이 방식의 이점: 이름 목록 없이 동작하고, 사용자를 막다른 길에 두지 않고,
차단 사유를 설명할 수 있습니다.
한계도 명시합니다: 오탐이 생깁니다(일반 명사가 이름 자리에 올 수 있음).
그래서 `transform`은 차단이 아니라 안내이며, `block`만 강하게 막습니다.

**검증** `domain/rights.js`의 `screenRequest()` + 테스트 5개.

## 15. AI 투명성 의무의 구현 형태

**문제**
§15은 "적절한 경우 AI 생성 고지"라고만 합니다. §25는 EU AI Act를 참조 기준으로 들지만,
"적절한 경우"는 구현 지시가 아닙니다.

**결정** 고지를 4곳에 **항상** 넣습니다(조건부 아님).

1. 전달·다운로드 화면의 사람이 읽는 고지
2. 함께 내려가는 `provenance.json`(모델·씨드·수정 이력·인적 기여·유사도 판정)
3. 공유 페이지의 고지
4. 라이선스 영수증의 고지 문단

**한계를 명시**: WAV/MP3에 대한 콘텐츠 자격증명(C2PA) 임베딩은 컨테이너 지원과
플랫폼 보존이 불완전합니다. 그래서 v1.1은 **동봉 파일 + 서버측 기록**을 1차 수단으로 하고,
컨테이너 내 마킹은 표준 성숙도를 추적하는 항목으로 둡니다.
"메타데이터를 넣었다"고 적어두고 실제로는 유통 과정에서 사라지는 것이 더 나쁩니다.

**인적 기여 기록**(§16.3 대응): 가사 수정 거리, 잠근 줄 수, 제공한 사실 개수,
수정 요청 횟수, 선택한 버전, 스토리 반영도를 모두 남깁니다.
저작권 성립을 **주장하지 않되**, 판단에 필요한 사실은 보존합니다.

**검증** `domain/rights.js`의 `buildProvenance()`, 라이선스 영수증 텍스트,
공유 페이지, `provenance.json` 다운로드.

## 16. 일정과 가격의 근거

**문제**
§21의 "1인 개발자 11–13주"에는 결제·세금·약관·보컬 조달·법무 대기 시간이 빠져 있습니다.
§19의 개인 29,000원 / 상업 89,000원에도 원가 근거가 없습니다.

**결정 — 일정**
기술 구현은 11–13주가 타당합니다. 다만 다음을 별도 항목으로 세웁니다.

| 항목 | 추가 |
|---|---|
| 결제·세금·환불 처리(국내 PG, 현금영수증/세금계산서, 청약철회 예외 고지) | +2주 |
| 약관·개인정보처리방침·라이선스 문안 법무 검토 | +1~3주 (대부분 **대기 시간**) |
| 보컬 조달 결정(스톡 보이스 계약 시) | Phase 0에 추가, 계약 리드타임 별도 |

현실 범위: **기술 14–17주 + 법무 대기**. 그리고 Phase 0의 종료 조건을
"평가했다"가 아니라 **"준비 게이트 6개 필드가 계약서로 채워졌다"**로 바꿉니다(§8).

**결정 — 가격**
MVP는 v1.0 제안대로 **고정 패키지 2종**을 유지합니다(토큰 지갑 없음: 옳은 판단).
다만 가격 확정 절차를 정의합니다.

1. 원가 원장(`CostLedgerEntry`)으로 완성 프로젝트당 실제 원가를 30건 이상 수집
2. 목표 매출총이익률(권장 70% 이상)과 **포함 수정 횟수의 원가 탄력성**을 계산
3. 그 다음 가격 확정. 포함 수정 횟수는 가격이 아니라 **원가로** 정한다

무료 재생성 1회를 정책으로 두는 순간 원가의 분산이 커지므로, "결함" 판정 기준을
미리 정의합니다: 생성 실패, 무음/클리핑, 유사도 격리, 승인된 가사와 불일치,
선택한 스펙과 명백한 불일치. **취향 불일치는 결함이 아닙니다**(그래서 A/B와 수정 2회가 있습니다).

**환불 남용 경로**도 정의합니다: 최종 파일 다운로드 후에는 결함 확인 시에만 환불,
환불 시 라이선스는 소급 실효되고 공유 링크는 폐기됩니다.

## 부록 A — 프로토타입이 증명한 것과 증명하지 못한 것

이 리포지토리의 `soundfit/`은 상용 음악 API 없이 **브라우저에서 직접 소리를 합성**해
전체 흐름을 돌립니다. 목적은 음악 품질이 아니라, 위 결정들이 실제로 성립하는지
프로바이더 계약 **전에** 확인하는 것입니다.

**증명된 것** (자동 테스트 57개 + 헤드리스 브라우저 실측)

| 주장 | 실측 |
|---|---|
| 구간 단위 수정이 국소적이다 | 후렴 수정 → 10구간 중 **3구간**만 재렌더(21초) |
| 가사 한 줄 수정도 국소적이다 | verse2 **1구간**만 dirty |
| 구조 변경은 정직하게 전체 재생성 | 기타 솔로 추가 → `structural: true` |
| A/B 차이가 통제·설명 가능하다 | 선언된 2축 외 모든 필드 동일함을 테스트로 강제 |
| 금지 항목이 승인을 차단한다 | 가사에 금지어 삽입 시 `canApprove:false` |
| 인물 음성 요청이 막힌다 | 복제·고인·완전복사 → `block`, "~처럼" → `transform` |
| 추론이 명시적 선택을 덮지 않는다 | 신호 1건은 확신도 상한 0.44로 미적용, 90일 반감기 |
| 유료 요청이 멱등하다 | 동일 키 재호출 시 재생 경로, stale in-flight 회수 |
| 상태 기계가 불법 전이를 막는다 | 전이 검증 + 11단계 실측 이력 |
| 원가를 스테이지별로 계측한다 | 가사/생성A/생성B/수정 4행 원장 기록 |
| 마스터링이 레벨을 맞춘다 | 피크 −1.0 dBFS, RMS −14.4 dBFS |

**증명되지 못한 것** (여기서 판단하면 안 되는 것)

- **음악적 품질**: 절차적 합성이며 상용 생성 모델의 대체물이 아닙니다.
- **보컬**: 포먼트 합성 가이드입니다. 사람의 노래가 아닙니다.
- **가사**: 언어 모델이 아니라 템플릿 엔진입니다. 교체 가능한 어댑터 경계만 증명합니다.
- **유사도**: 상징적 멜로디 검사입니다. 오디오 지문이 아닙니다.
- **성능**: 샌드박스 컨테이너에서 190초 곡 = 렌더 28초(약 6.7배속, 노트 2,167개).
  일반 노트북에서는 더 빠르지만, **실제 지연은 프로바이더 API가 결정**합니다.
- **결제·세금·다중 사용자·저장소 보안**: 전부 미구현(localStorage).
- **고객 반응**: 이건 코드로 알 수 없습니다.
